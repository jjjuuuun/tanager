2.언어와 기술 스택

2.1 Python 과 Java 비교

이 프로그램에서 가장 어려운 부분은 기능 자체가 아니라 터미널 에뮬레이션(VT 시퀀스, 색, 와이드 문자, 한글 IME)과 PTY(Windows ConPTY, Unix pty)다. 언어는 이 두 가지를 얼마나 믿을 만한 라이브러리로 해결할 수 있는지로 골랐다.

기준Java 25 + Swing + JediTerm + pty4jPython + Textual + pyte + pywinpty
터미널 에뮬레이션유리 JediTerm: JetBrains IDE 내장 터미널에서 쓰는 에뮬레이터보통 pyte: 순수 Python, 대량 출력 시 느림
PTY (Windows / Unix)유리 pty4j 하나로 Windows·macOS·Linux보통 pywinpty 와 ptyprocess 를 따로 감싸야 함
한글 IME · 와이드 문자유리 Swing 입력기 지원(M0 에서 검증)불리 터미널 안의 터미널이라 IME 를 호스트 터미널에 의존
화면 구조데스크톱 창: 좌측 트리 + 중첩 분할 터미널TUI: tmux 를 처음부터 다시 만드는 수준
실행 파일jpackage 로 JRE 포함 .exe·.msi·.dmgPyInstaller/Nuitka, 백신 오탐 사례 잦음
macOS 확장같은 라이브러리, 플랫폼 모듈만 추가가능하지만 PTY·입력 처리 분기 증가
함수형 + 객체지향 표현record · sealed · 패턴 매칭 · 가상 스레드dataclass · match · 타입 힌트(런타임 강제 없음)
개발 속도보통유리
결정: Java 핵심 가치(경로 이력·레이아웃·복원)에 집중하고, 에뮬레이터와 PTY 는 검증된 라이브러리에 맡긴다. 상세 근거와 검증 조건은 docs/adr/0001-java-swing-jediterm-pty4j.md. M0 스파이크에서 검증에 실패하면 ADR 을 대체하고 다시 고른다.
"GUI 가 아니라 그냥 터미널이어도 괜찮다"에 대해 메인 영역의 각 창(pane)은 실제 셸이 도는 터미널 화면이다. 그 바깥(좌측 트리, 분할 경계, 탭)만 데스크톱 창이 맡는다. 순수 TUI 로 만들면 터미널 안에서 다시 터미널을 에뮬레이션해야 해서 한글 입력과 성능에서 손해가 크다.

4.개발 방법론: DDD · TDD · 헥사고날

DDD 와 TDD 는 고르는 대상이 아니다. DDD 는 무엇을 어떻게 나눌지, TDD 는 나눈 것을 어떤 순서로 만들지, 헥사고날은 어디에 둘지를 정한다. 이 프로젝트는 세 가지를 다 쓰되, 규모에 맞게 가볍게 쓴다.

질문방법이 프로젝트에서 하는 일하지 않는 일
무엇을 나눌까DDD 전략 설계바운디드 컨텍스트 6개(history · layout · session · workspace · toolkit · monitor), 유비쿼터스 언어(SDD 용어집) 를 코드 이름에 그대로 쓴다컨텍스트별 별도 서비스·DB
모델은 어떻게DDD 전술 패턴애그리거트(WorkHistory, Tab), 값 객체(WorkspacePath, Ratio), 도메인 이벤트, 애그리거트 단위 저장소팩토리·도메인 서비스 남발, CQRS·이벤트 소싱
어떤 순서로TDD행위 하나씩 RED → GREEN → REFACTOR. 계층마다 방식이 다르다(아래)테스트 없는 프로덕션 코드
어디에 둘까헥사고날 (포트 & 어댑터)도메인·유스케이스는 포트만 알고, OS·라이브러리는 어댑터에 격리어댑터 간 직접 호출
모르는 게 많을 때스파이크spike/ 브랜치에서 테스트 없이 빠르게 확인 → 결론은 ADR → 코드는 버리고 TDD 로 다시스파이크 코드를 main 에 병합

5.코드 작성 규칙: 객체지향 + 함수형

답은 둘 다, 자리를 나눠서다. 규칙(계산)은 함수형으로, 경계(자원·I/O·화면)는 객체지향으로 쓴다. 이 구조를 Functional Core, Imperative Shell 이라고 부른다.

위치패러다임상태대표 기법
domain함수형불변record, sealed interface, switch 패턴 매칭, Result, Optional
application함수형 계산 + 얇은 명령형 조율StateActor 안에서만 교체유스케이스 = 포트 호출 → 순수 계산 → 포트 호출
adapter · platform · ui · app객체지향가변(캡슐화)SOLID, 인터페이스 구현, 합성, 자원 수명 관리(AutoCloseable)

5.1 예: 레이아웃 트리 (도메인, 함수형)

public sealed interface LayoutNode {

    record Leaf(PaneId pane) implements LayoutNode {}

    record Split(Orientation orientation, Ratio ratio, LayoutNode first, LayoutNode second)
            implements LayoutNode {}

    /** target 창을 둘로 나눈 새 트리를 돌려준다. 원래 트리는 바뀌지 않는다. */
    default LayoutNode split(PaneId target, Orientation o, PaneId created) {
        return switch (this) {
            case Leaf(var p) when p.equals(target) -> new Split(o, Ratio.HALF, this, new Leaf(created));
            case Leaf _ -> this;
            case Split(var or, var r, var a, var b) ->
                    new Split(or, r, a.split(target, o, created), b.split(target, o, created));
        };
    }
}

5.4 규칙 요약

전체 목록은 .claude/rules/java-style.md. Java 파일을 열면 Claude 에게 자동으로 로드된다.

  1. 값·이벤트·DTO 는 record, 불변식은 compact constructor 에서 검증
  2. 닫힌 계층은 sealed, switch 는 default 없이 전부 처리
  3. null 금지 → Optional / Result
  4. 도메인 오류는 예외가 아니라 sealed 값
  5. 상태 변경 메서드는 새 값을 반환, 세터 금지
  6. 클래스는 기본 final, 상속보다 합성
  7. 가변 상태는 어댑터와 StateActor 안에만, static 가변 필드 금지
  8. Swing 은 EDT 에서만, PTY 읽기는 세션당 가상 스레드
  9. OS 분기는 tanager-app 의 플랫폼 선택 한 곳에만
  10. 명령어 내용·출력은 저장·로그 금지, 경로만 기록
  11. 사용자 AI 도구 설정 파일은 읽기만, 비밀값은 어댑터에서 마스킹

6.Git 브랜치 전략

6.1 선택: dev(통합) + main(릴리스 전용) — Git Flow 간소화

개발은 전부 dev 에서 한다. 작업 브랜치는 dev 에서 갈라져 PR 로 dev 에 squash merge 된다. 마일스톤이 끝나면 dev → main 릴리스 PR 을 merge commit 으로 병합하고 main 에 태그를 붙인다. 그래서 main 은 언제나 "마지막으로 배포한 버전"과 같다. Git Flow 의 release/* 브랜치는 두지 않는다 — 버전은 태그에서 빌드에 주입하므로 릴리스 준비 커밋이 없다(ADR-0004).

6.2 브랜치 이름과 병합 방법

브랜치형식갈라지는 곳 → 들어가는 곳병합 방법 · 수명
mainmain— (릴리스만 받음) · GitHub 기본 브랜치영구. 직접 커밋·푸시 금지. 태그는 여기에만
devdevmain 에서 1회 생성 · 통합 브랜치영구. 직접 커밋·푸시 금지
작업<type>/<이슈번호>-<kebab-slug>
feat/12-split-pane-resize		dev → devSquash and merge, 1~3일 목표, 병합 후 삭제

긴급 수정hotfix/<이슈번호>-<slug>main → mainCreate a merge commit → 패치 태그 → 역병합 PR main → dev(merge commit)
실험spike/<이슈번호>-<slug>dev → (병합 금지)CI 가 차단. 결론은 ADR
팀 하위<부모 브랜치>--<역할>부모 → 부모로컬 병합. PR 없음
태그vMAJOR.MINOR.PATCH[-pre]main 의 커밋release 워크플로 트리거(main 위가 아니면 실패)

작업 type: feat fix perf refactor test docs build ci chore spike (+ hotfix). 검사: .githooks/pre-commit · pre-push(main·dev 직접 커밋·푸시 차단, 이름 규칙), .github/workflows/pr-lint.yml(head → base 조합과 제목). 릴리스 · 역병합 PR 이 merge commit 인 이유: squash 하면 dev 와 main 의 이력이 갈라져, 다음 릴리스 PR 에 같은 변경이 다시 나오거나 충돌한다.

6.3 GitHub 저장소 설정 (.github/scripts/bootstrap-repo.sh)

사용자가 저장소를 처음 만들 때 한 번 실행한다. 빈 시작 커밋 → dev 생성 → 푸시 → 아래 설정 → 라벨 · 마일스톤. Claude 는 이 스크립트를 실행할 수 없다(시작 커밋에만 훅 우회가 필요하기 때문).

저장소

  • 기본 브랜치: main (작업 PR 은 --base dev 명시, dev 병합 시 close-issues.yml 이 이슈를 닫음)
  • Squash merge · Merge commit 허용, Rebase merge 끔
  • Squash/merge 커밋 메시지 = PR 제목과 본문
  • 병합 후 head 브랜치 자동 삭제

브랜치 규칙 (ruleset)

  • main: PR 필수, 허용 병합 = merge commit, 삭제 · 강제 푸시 금지
  • dev: PR 필수, 허용 병합 = squash · merge commit, 삭제 · 강제 푸시 금지
  • 승인 인원 0명 (혼자 개발 — 자기 PR 은 승인할 수 없다)
  • 필수 CI 검사(lint · test-core · test-windows · pr-lint)는 M1 이후 --with-checks 로 켠다
비공개 저장소 + 무료 플랜ruleset 이 동작하지 않는다. 스크립트는 경고만 내고 넘어가며, 그때는 로컬 git 훅과 Claude 훅(guard-git.sh)만으로 main · dev 를 지킨다.

6.4 버전 규칙 (SemVer)

릴리스 PR(dev → main)에 담긴 커밋다음 버전
feat(...)!: 또는 footer BREAKING CHANGE:MAJOR (v1.0.0 전에는 MINOR)
featMINOR
fix, perfPATCH
그 외버전 변화 없음 (다음 릴리스에 묻어 감)

Breaking 의 기준: 저장 파일(state.json, config.json)을 이전 버전이 못 읽게 되거나, 기본 키 바인딩·셸 통합 동작이 바뀌는 경우.

7.2 커밋 시점 (이 순서대로)

  1. RED — 실패 테스트 작성 → 커밋하지 않는다빨간 상태의 커밋은 bisect 를 망가뜨린다.
  2. GREEN — 테스트가 통과한 직후 커밋feat 또는 fix. 테스트와 구현을 한 커밋에 담는다.
  3. REFACTOR — 전체 테스트 GREEN 확인 후 별도 커밋refactor. 동작 변경이 섞이면 안 된다. 바꿀 것이 없으면 생략.
  4. 빌드 · CI · 문서 · 설정 변경은 각각 따로 커밋build / ci / docs / chore. 기능 커밋에 섞지 않는다.
  5. 푸시는 PR 을 열 준비가 됐을 때, 또는 하루 작업을 마칠 때pre-push 훅이 ./gradlew check 를 돌린다. 브랜치에 올린 뒤에는 rebase 후 --force-with-lease 만 허용.
금지RED 상태 커밋 · 포맷과 로직 혼합 · 리팩터링과 기능 혼합 · 빌드 산출물 커밋 · --no-verify

8.PR 절차와 템플릿

8.1 역할 분담

Claude 가 하는 것

  • 이슈 생성(/issue) · 마일스톤 지정
  • 브랜치 · TDD 커밋(/tdd) · 푸시
  • Draft PR · CI 대응 · 리뷰 후 PR 에 리뷰 코멘트(병합 권장/보류 권장) · Ready 전환(/pr)
  • 작업 PR 의 dev squash 병합 — CI green · 차단 0건 · "병합 권장"일 때만
  • 릴리스 PR dev → main — 포함된 PR · 리뷰 권고 · 남은 지적 · 수동 확인 항목을 모아 정리(/release)
  • 사용자 승인 후 태그 생성 · 푸시 · 마일스톤 닫기

사용자가 하는 것

  • 마일스톤마다 한 번, 릴리스 PR 을 보고 main 병합 결정 — 사용자 확인 지점(ADR-0005)
  • hotfix → main · 역병합 PR 병합, PR 닫기, Claude 가 넘긴(보류 권장) 작업 PR 결정
  • 태그 생성 · 태그 푸시 승인 (승인 창)
  • 저장소 최초 설정 bootstrap-repo.sh
  • Claude 가 확인할 수 없는 수동 확인(실제 화면 · 한글 입력 · 설치 파일)

강제: gh pr merge 는 PR 의 base 가 dev 이고 --squash 일 때만 guard-git.sh 가 통과시킨다(base 를 조회). gh pr close · gh pr review --approve 는 settings.json deny + guard-git.sh 차단. 태그 · 태그 푸시 · gh release create 는 allow 규칙과 상관없이 승인 창(guard-git.sh 가 ask 반환).

8.2 작업 PR 절차 (이 순서대로)

  1. 이슈 생성 — Claude/issue. 템플릿 필드 · 인수 조건 Given/When/Then · SDD 요구사항 ID → 마일스톤(.github/milestones.json).
  2. 브랜치 생성 — Claudegit switch dev && git pull --ff-only → git switch -c feat/12-split-pane-resize
  3. TDD 사이클 커밋 반복 — Claude§7.2 순서. /tdd 12 분할 비율 조정.
  4. dev 최신화 · 로컬 전체 검사 — Claudegit rebase origin/dev → ./gradlew check
  5. 푸시 → Draft PR (base dev) — Claude/pr. 본문 첫 줄 "병합 방법: Squash and merge", 템플릿 1~9절, 이슈와 같은 마일스톤.
  6. CI 전부 green — Claudelint · test-core · test-windows · pr-lint. 실패하면 고쳐서 다시 푸시.
  7. 리뷰 → PR 에 리뷰 코멘트 — Claudereviewer 서브에이전트 + /code-review. 차단 지적은 고친 뒤, 최종 결과와 권고를 gh pr review --comment 로 남긴다.
  8. Ready for review — ClaudeDraft 해제.
  9. Squash merge — Claude (조건부)CI green · 차단 0건 · 권고 "병합 권장"이면 gh pr merge <n> --squash --delete-branch. PR 제목이 dev 의 커밋 헤더가 된다. 조건이 하나라도 안 맞으면 병합하지 않고 사용자에게 넘긴다.

8.3 릴리스 절차 (마일스톤이 끝났을 때)

  1. 준비 확인 — Claude/release: 마일스톤의 열린 이슈 0개 · dev CI green · main 이 dev 의 조상인지(역병합 누락 확인).
  2. 릴리스 PR dev → main — Claude제목 chore(release): v0.3.0, 본문 첫 줄 "병합 방법: Create a merge commit", git-cliff 변경 내역, 호환성, WSL 통합 테스트 결과. 릴리스 리뷰 코멘트.
  3. 사용자 확인 지점: merge commit 으로 병합 또는 보류 — 사용자마일스톤의 모든 작업 PR 을 여기서 한 번에 본다. 본문의 "포함된 PR" 표와 "사용자가 직접 확인할 것" 체크박스.
  4. 태그 — Claude, 승인 후main 에서 git tag -a v0.3.0 → git push origin v0.3.0 (각각 승인 창) → release 워크플로 → 마일스톤 닫기.

8.4 긴급 수정 (hotfix)

배포된 버전의 치명적 버그만. hotfix/31-restore-crash 를 main 에서 갈라 8.2 와 같이 진행하되 base 는 main, 병합 방법은 merge commit. 병합되면 패치 태그(v0.3.1)를 붙이고, Claude 가 역병합 PR(main → dev, chore(release): v0.3.1 역병합)을 연다.

11.3 에이전트 팀

Claude Code 의 에이전트 팀은 실험 기능이며 기본으로 꺼져 있다. 메인 세션이 리드가 되어 팀원을 띄우고, 팀원은 .claude/agents/ 의 정의를 이름으로 재사용할 수 있다.

켜는 법 (개인 설정)

// .claude/settings.local.json  (커밋하지 않음)
{
  "env": { "CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS": "1" }
}

팀 운영 순서

  1. architect 가 포트를 먼저 고정팀원 사이의 계약. 포트 변경은 리드만 한다.
  2. 리드가 모듈 단위로 작업을 나눔한 모듈은 한 팀원만 고친다 → 파일 충돌 방지.
  3. 팀원별 worktree · 하위 브랜치feat/40-restore--domain 등. 각자 TDD 로 커밋.
  4. 리드가 부모 브랜치로 병합 후 ./gradlew check충돌·계약 위반은 리드가 해결.
  5. reviewer → /pr부모 브랜치 → dev PR. 이후는 §8.2 절차와 같다.
제약 세션 하나에 팀 하나, 중첩 팀 없음, in-process 팀원은 세션 재개가 안 되고, 팀원별 권한 모드를 따로 줄 수 없다. 토큰 사용량이 크게 늘어난다. 팀 기능을 켜 두면 Claude 가 서브에이전트 대신 팀원을 띄울 수 있으므로 쓰지 않을 때는 끈다.
